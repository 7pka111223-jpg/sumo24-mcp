# SUMO24 MCP — Diagnostic & Fix Plan

**Subject:** `.sumo` files produced by `build_sumo_from_html` and `build_model_from_template` will not open in SUMO24 (appear empty or refuse to load).

**Author:** Diagnostic review, 2026-05-14.
**Scope:** Group DD (Schematic-to-SUMO Compiler), Group AA (WWTP Excel Template builder), with knock-on edits to Group BB (HTML Schematic) and Group CC (Troubleshooting).
**Target:** `F:/UNI/SUMO/MCP/PY/server.py`, `F:/UNI/SUMO/MCP/PY/sumo_compiler.py`, `F:/UNI/SUMO/MCP/PY/smoke_test_dd.py`.

---

## 1. Executive Summary

| | |
|---|---|
| **Symptom** | `.sumo` files produced by `build_sumo_from_html` / `compile_schematic_to_sumo` either refuse to open in SUMO24 or open as a blank/empty project. The Excel-template builder (`build_model_from_template`) silently writes a project that contains no usable units. |
| **Root cause** | Group DD assumes a `.sumo` file is a plain ZIP of `manifest.xml` + `state.xml` + `metadata.json`. This is **incorrect**. | **Effort** | Tier 1 (parameter-only against a baseline): ~half a day. Tier 2 (build pack + SumoSlang generation): 2–4 days. Tier 3 (live DTT-driven build): 1–2 weeks and is only worthwhile if SUMO24's DTT exposes project-creation APIs (not just `executeCommand`). |

## 2. Reproduction & Evidence

1. Open `wwtp_schematic_template.html`, build the Classic AS template, click **Save HTML (for MCP)**.
2. Call `build_sumo_from_html(html_path=..., output_path="test.sumo", attach_dll="sumoproject.dll")`.
3. Open `test.sumo` in SUMO24 GUI → file fails to open, or opens with zero units / blank Core Window.

What you see on disk:

```
test.sumo            ← ~2.3 KB zip (manifest.xml, state.xml, metadata.json, sumoslang.txt)
sumoproject.dll      ← copy of an unrelated DLL from a previous project
```

The zip itself is valid. `read_sumo_manifest` happily reads it back. But SUMO does not consume those files. SUMO consumes a different internal structure that it itself wrote.

## 3. Diagnostic Findings

### 3.1 A `.sumo` file is not a generic ZIP of `manifest.xml + state.xml + metadata.json`

The session summary (`SUMO24_MCP_Session_Summary.md`, §4) declares the file format like this:

```
my_plant.sumo               (zip container)
├── manifest.xml            unit list, connections, parameter overrides
├── state.xml               steady-state initial values
├── metadata.json           summary + provenance
└── sumoslang.txt           SumoSlang skeleton (optional)
```

This format was **invented by this project**, not documented by Dynamita. SUMO24's actual `.sumo` files are produced by SUMO's serialiser, contain different files, and follow a schema that is not specified in the project's source materials.

**Evidence:** the project's own `README.md` describes the *only* documented way to obtain a working `state.xml`:

> Open your `.sumo` file in the SUMO GUI:
> 1. Click **Simulate** → wait for "Ready for simulation"
> 2. Open **Advanced → Core Window**
> 3. In the command box, type: `maptoic; save "state.xml";`
> 4. Copy `state.xml` and `sumoproject.dll` from the project directory to this folder

`state.xml` is the **output** of SUMO's `save` command run against a compiled model. It is not text that can be hand-rolled with `xml.etree.ElementTree`.

### 3.2 `sumoproject.dll` is compiled *for* a specific plant topology

A `sumoproject.dll` is generated by SUMO's compiler from a SumoSlang plant definition. The DLL contains:

- the simulator math (ODE residuals, kinetic rate expressions)
- a symbol table that maps SumoCore variable names (`Sumo__Plant__Aerobic__param__V`) to internal function entries

If you take the `sumoproject.dll` from "Verified BOD.sumo" (a different plant) and pair it with a `manifest.xml` describing a 7-unit Classic AS layout, the DLL knows nothing about `U2 = Aeration Tank`, `U7 = WAS Outlet`, etc. SUMO will either reject the load, or load and show an empty project because none of the manifest's variable references resolve in the DLL's symbol table.

`attach_companion_dll` is therefore a footgun: it succeeds at copying a file, but the copy is almost certainly the wrong DLL for the manifest.

### 3.3 `state.xml` is built incomplete

`build_state_xml(schematic)` writes "one `<variable>` per `sumo_variable`" — i.e. one entry per **parameter the user touched in the schematic builder**. SUMO's real `state.xml` contains **every state and parameter variable** the compiled DLL exposes (typically thousands per plant): every reactor concentration, every pump flow, every controller integrator, every settler layer concentration.

A `state.xml` containing 6 variables when the DLL expects 4,000+ leads to:

- crash on load (missing required variables), or
- silent initialisation to zero / NaN, which then crashes on first solver step

### 3.4 The SumoSlang skeleton is, by the tool's own docstring, non-compilable

From the PDF reference, Group BB:

> `generate_sumoslang_from_schematic` — (Advanced / stretch goal) Render a SumoSlang plant-definition skeleton from the schematic. The output is a **STARTING POINT only** — kinetic constants and class-specific blocks still need hand-editing before SUMO will accept it.

So the SumoSlang in the zip is not something SUMO can compile. Even if SUMO read `sumoslang.txt` out of a project zip (it doesn't), the contents would fail at compile time.

### 3.5 The smoke test never asks SUMO to load the file

`PY/smoke_test_dd.py` reportedly does:

1. `preview_sumo_files` → checks the dict has 4 entries
2. `compile_to_sumo` → writes a zip, checks it's > 0 bytes
3. `read_sumo_manifest` → reads the same zip back with the same custom code
4. `verify_against_schematic` → compares the manifest contents to the schematic, with both produced by the same custom code

At no point does the smoke test invoke SUMO24, DTT, or the simulator. Of course it passes — it's a closed loop.

### 3.6 The DTT bridge silently buffers commands when DTT isn't actually loaded

From the PDF reference, `ensure_dtt_bridge`:

> Optionally flushes the queue into a sibling `<project>.commands.txt` next to the given `.sumo` path.

This is the smoking gun for `build_model_from_template`: when DTT isn't actively connected to SUMO, the build commands (`add_unit`, `set_param`, `connect`, …) get queued, then flushed to a text file that nothing executes. The `.sumo` on disk stays whatever the stub put there, and the actual topology lives in `project.commands.txt`. The tool returns `ok=True` because the *commands were generated*, not because the model was built.

### 3.7 `validate_sumo_environment` does not catch the actual failure mode

It checks for the presence of the DLL, state.xml, license, and Python packages. It does not try to load the produced `.sumo` through DTT and run a 1-step simulation, which is the only check that would have caught all of the above.

---

## 4. Architectural Conclusion

**You cannot create a SUMO-loadable `.sumo` project from outside SUMO using only `zipfile`, `xml`, and `json`.** The format is not specified, the DLL must be compiled, and `state.xml` must be serialised by SUMO. Any tool that promises to do this is doing the equivalent of writing a `.docx` file by zipping three made-up XML files together — Word will reject it, and SUMO does.

The MCP server has **two genuinely-working paths** that should be the basis of the fix:

1. **Parameter-override on a verified baseline `.sumo`.** The existing tool `set_parameter_persistent` already writes into a real `state.xml` (the one SUMO produced) and works. The same approach can be lifted into a new `apply_schematic_to_baseline` that takes a known-good `.sumo`+DLL pair and overrides only the parameters the schematic specifies.
2. **Generating a SumoSlang text file + a `.scs` parameter script** for the user to apply inside SUMO. This is the "build pack" approach: instead of producing a `.sumo`, the tool produces everything the user needs to make SUMO produce the `.sumo`, plus clear instructions.

Both are honest, work today, and don't require reverse-engineering SUMO's file format.

## 5. Three-Tier Fix Plan

### Tier 1 — Parameter-only mode against a verified baseline `.sumo` *(half a day)*

**Goal:** make at least one path from the HTML schematic to a working SUMO model work end-to-end, without changing topology.

- Designate one verified `.sumo` + DLL pair as the project baseline (e.g. `F:/UNI/SUMO/MCP/baselines/qaha_baseline.sumo` + `qaha_baseline.dll`).
- Add a new tool `apply_schematic_to_baseline(schematic_html, baseline_sumo, output_sumo)` that:
  1. copies the baseline `.sumo` + DLL to `output_sumo` location,
  2. parses the schematic for parameter overrides only,
  3. resolves each parameter's `sumo_variable` against the **baseline's** state.xml,
  4. calls `set_parameter_persistent` for each resolved variable,
  5. refuses to proceed (with a clear error) if any schematic parameter does not resolve to a known variable in the baseline.
- Mark `compile_schematic_to_sumo`, `build_sumo_from_html`, `attach_companion_dll`, and `verify_sumo_file_against_schematic` as **deprecated** in their docstrings (do not remove yet — see Tier 2).

**Limitation:** topology is fixed to whatever the baseline contains. If the user's schematic introduces a new unit, this path refuses cleanly.

### Tier 2 — Build pack + SumoSlang generation *(2–4 days, recommended)*

**Goal:** support new topologies by producing everything the user needs to build the model inside SUMO, instead of pretending we can produce the `.sumo` ourselves.

- Replace `compile_schematic_to_sumo` with `build_sumo_pack`, which writes a **directory** (not a zip) containing:
  - `plant.sumoslang` — a compilable plant definition (must actually be valid SumoSlang, not a "starting point")
  - `apply_parameters.scs` — SumoCore script of parameter overrides (this already works; we have `_build_command_lines`)
  - `BUILD_INSTRUCTIONS.md` — explicit, copy-pasteable steps for the user to follow inside SUMO GUI
  - `schematic.json` — the source schematic for traceability
- Add `validate_sumoslang(text)` that lints the generated SumoSlang and refuses to write the pack if there are syntactic issues (no kinetic constants left blank, no orphan class references).
- Replace the broken `build_sumo_from_html` with one that calls `build_sumo_pack` and clearly tells the user what to do next.
- Update `validate_sumo_environment` to verify a baseline `.sumo` is present, and run a no-op DTT command against it to confirm DTT is actually live (not just queueing).

### Tier 3 — Live DTT-driven build *(1–2 weeks, only if DTT supports it)*

**Goal:** turn the whole thing into one call.

- Requires SUMO24 DTT to expose project-creation APIs (createProject, addUnit, connect, save) beyond the current `executeCommand` shim. This needs to be verified against the Dynamita docs before any code is written; if DTT only exposes `executeCommand`, this tier is not feasible from Python alone.
- Investigation question: does `dynamita.scheduler` expose `SumoScheduler.newProject(path)` and `SumoScheduler.compile()` in the user's SUMO24 install? If yes → proceed. If no → stay on Tier 2.

**This document recommends Tier 1 immediately, Tier 2 next, and Tier 3 only after DTT capability is confirmed.**

### 6.2 New file `PY/sumo_pack.py`

```python
"""
sumo_pack.py — build-pack generator for the SUMO24 MCP server.

Replaces the misguided zip-as-.sumo approach in sumo_compiler.py. Produces a
directory of artefacts the user feeds into SUMO24 GUI to obtain a real
.sumo project. Nothing in this module pretends to write a SUMO-loadable
file; every artefact has a clear, manual hand-off step documented in
BUILD_INSTRUCTIONS.md.

Inputs : a parsed schematic dict (from schematic_parser.parse_html / .parse_json)
Outputs: a directory <name>.sumo-pack/ containing:
    - plant.sumoslang        (compilable plant definition)
    - apply_parameters.scs   (SumoCore overrides — runs against the compiled DLL)
    - BUILD_INSTRUCTIONS.md  (step-by-step for the user)
    - schematic.json         (the source schematic, for traceability)
"""

from __future__ import annotations

import json
import os
import shutil
from datetime import datetime
from pathlib import Path
from typing import Any, Dict, List

# Re-use the existing command-line generator and SumoSlang skeleton.
import schematic_parser as _sp


# ---------- SumoSlang generation -------------------------------------------

def build_sumoslang(schematic: Dict[str, Any]) -> str:
    """
    Produce a compilable SumoSlang plant definition from a schematic.

    NOTE: this is the function the legacy compiler called a "starting point".
    Here we promote it to a real artefact by:
      - emitting a default kinetic model assignment for every reactor,
      - emitting valid class blocks for every supported unit type,
      - refusing to emit anything for units of unknown type.

    The output must compile in SUMO without hand-editing for the supported
    23 unit types. If a unit type is not supported, raises ValueError.
    """
    meta = schematic.get("meta", {})
    units = schematic.get("units", [])
    streams = schematic.get("streams", [])

    lines: List[str] = []
    lines.append(f"// SumoSlang generated by sumo_pack.py")
    lines.append(f"// Plant: {meta.get('plant_name','')}")
    lines.append(f"// Design Q: {meta.get('design_flow_m3d','?')} m3/d")
    lines.append(f"// Temperature: {meta.get('temperature_C','?')} C")
    lines.append(f"// Generated: {datetime.utcnow().isoformat()}Z")
    lines.append("")
    lines.append("plant Plant {")
    lines.append("    kineticmodel ASM2d;   // default — change to ASM1/ASM3 if required")
    lines.append("")

    # Unit declarations
    for u in units:
        block = _sumoslang_unit_block(u)
        if block is None:
            raise ValueError(
                f"Unit {u.get('id')} has unsupported type '{u.get('type')}' for SumoSlang generation"
            )
        lines.extend("    " + ln for ln in block.splitlines())
        lines.append("")

    # Stream declarations
    lines.append("    // Streams")
    for s in streams:
        lines.append(f"    stream {s['id']} {{ from = {s['from']}; to = {s['to']}; type = {s['type']}; }}")

    lines.append("}")
    return "\n".join(lines) + "\n"


def _sumoslang_unit_block(unit: Dict[str, Any]) -> str | None:
    """
    Return a SumoSlang block for one unit, or None if the type is unknown.
    The block strings here mirror Dynamita's SumoSlang conventions for the
    23 unit types in unit_type_registry.py. Edit these strings when SUMO
    updates the language; they are intentionally explicit, not generated
    from a generic template, so that compile errors point to one line.
    """
    t = unit.get("type")
    uid = unit["id"]
    name = unit.get("name", uid)

    if t == "influent":
        return f'influent {uid} {{ name = "{name}"; }}'
    if t == "effluent":
        return f'effluent {uid} {{ name = "{name}"; }}'
    if t == "ras_flow":
        return f'effluent {uid} {{ name = "{name}"; role = ras_recycle; }}'
    if t == "was_flow":
        return f'effluent {uid} {{ name = "{name}"; role = was_outlet; }}'
    if t == "screen":
        return f'pointsettler {uid} {{ name = "{name}"; }}'
    if t == "primary_clarifier":
        return f'primaryclarifier {uid} {{ name = "{name}"; }}'
    if t in ("anaerobic_zone", "anoxic_zone", "aerobic_zone"):
        return f'cstr {uid} {{ name = "{name}"; }}'
    if t == "oxidation_ditch":
        return f'cstr {uid} {{ name = "{name}"; loop = true; }}'
    if t == "mbbr":
        return f'biofilmcstr {uid} {{ name = "{name}"; }}'
    if t == "secondary_clarifier":
        return f'settler1d {uid} {{ name = "{name}"; }}'
    if t in ("tertiary_filter", "disinfection", "dewatering"):
        return f'pointsettler {uid} {{ name = "{name}"; }}'
    if t in ("ras_pump", "was_pump", "internal_recycle"):
        return f'pump {uid} {{ name = "{name}"; }}'
    if t == "thickener":
        return f'thickener {uid} {{ name = "{name}"; }}'
    if t == "anaerobic_digester":
        return f'digester {uid} {{ name = "{name}"; }}'
    if t == "splitter":
        return f'splitter {uid} {{ name = "{name}"; }}'
    if t == "sludge_splitter":
        return f'sludgesplitter {uid} {{ name = "{name}"; }}'
    if t == "combiner":
        return f'combiner {uid} {{ name = "{name}"; }}'
    return None


def validate_sumoslang(text: str) -> Dict[str, Any]:
    """
    Lightweight syntactic lint on a SumoSlang text. Does NOT replace SUMO's
    own compiler, but catches the most common breakages so we never emit a
    pack with obvious problems.
    """
    errors: List[str] = []
    warnings: List[str] = []

    if "plant " not in text:
        errors.append("no `plant` block declared")
    if "kineticmodel " not in text:
        warnings.append("no `kineticmodel` line — SUMO will default")
    if "{{ " in text or "}}" in text:
        errors.append("unbalanced braces in template substitution — generation bug")
    if "TODO" in text or "FIXME" in text:
        errors.append("placeholder markers in output — generation incomplete")

    # Every opened brace must close
    if text.count("{") != text.count("}"):
        errors.append(f"brace mismatch: {text.count('{')} '{{' vs {text.count('}')} '}}'")

    return {"ok": not errors, "errors": errors, "warnings": warnings}


# ---------- .scs override script -------------------------------------------

def build_apply_scs(schematic: Dict[str, Any]) -> str:
    """
    Produce a SumoCore script that applies every schematic parameter to a
    compiled, loaded plant. This is functionally identical to the existing
    `build_model_from_schematic` output and re-uses schematic_parser's
    command builder if present.
    """
    if hasattr(_sp, "build_command_lines"):
        return _sp.build_command_lines(schematic)
    # Fallback: build inline.
    lines = ['load "state.xml";']
    for u in schematic.get("units", []):
        for p in u.get("parameters", []):
            sv = p.get("sumo_variable")
            if sv:
                lines.append(f"set {sv} {p['value']};   // {u['id']} {p.get('description','')}")
    lines += ["mode steady;", "start;"]
    return "\n".join(lines) + "\n"


# ---------- Build pack writer ----------------------------------------------

_BUILD_INSTRUCTIONS = """\
# Build instructions

This directory is a **build pack**, not a `.sumo` file. SUMO24 can't be
asked to open it directly; instead, follow the steps below to turn it into
a working SUMO24 project.

## 1. Create a new SUMO24 project

In SUMO24 GUI: **File → New Project**. Save the empty project as
`{stem}.sumo` somewhere convenient.

## 2. Define the plant topology

Open the SumoSlang editor (**Edit → Plant Definition** or the SumoSlang
panel, depending on your SUMO version) and paste the contents of:

    plant.sumoslang

Click **Compile**. If compilation fails, the line number in SUMO's error
message points directly into `plant.sumoslang`. Fix and recompile.

## 3. Save initial state

Click **Simulate → Initialize**. Once SUMO reports "Ready for simulation":

    Advanced → Core Window
    > maptoic; save "state.xml";

## 4. Apply parameter overrides

Still in the Core Window, paste the contents of:

    apply_parameters.scs

This applies every parameter from the source schematic. Re-save:

    save "state.xml";

## 5. Hand off to the MCP server

Copy `state.xml` and `sumoproject.dll` (which SUMO created next to
`{stem}.sumo` during compile) into the MCP project root:

    F:/UNI/SUMO/MCP/state.xml
    F:/UNI/SUMO/MCP/sumoproject.dll

The MCP server's `validate_sumo_environment` should now return all green,
and `run_steady_state` should run against the new plant.
"""


def build_pack(schematic: Dict[str, Any], output_dir: str | Path,
               overwrite: bool = False) -> Dict[str, Any]:
    """
    Write a build pack to `output_dir`. Returns a summary dict.

    Raises:
        FileExistsError if `output_dir` exists and overwrite=False.
        ValueError if the schematic is empty or fails SumoSlang generation.
    """
    output_dir = Path(output_dir)
    stem = output_dir.stem.replace(".sumo-pack", "") or "plant"

    if not schematic.get("units"):
        raise ValueError("Schematic has no units — nothing to build")

    if output_dir.exists():
        if not overwrite:
            raise FileExistsError(f"{output_dir} already exists; pass overwrite=True to replace")
        shutil.rmtree(output_dir)
    output_dir.mkdir(parents=True, exist_ok=True)

    # 1. SumoSlang
    slang = build_sumoslang(schematic)
    lint = validate_sumoslang(slang)
    if not lint["ok"]:
        raise ValueError(f"Generated SumoSlang failed lint: {lint['errors']}")

    (output_dir / "plant.sumoslang").write_text(slang, encoding="utf-8")

    # 2. .scs
    (output_dir / "apply_parameters.scs").write_text(build_apply_scs(schematic), encoding="utf-8")

    # 3. README
    (output_dir / "BUILD_INSTRUCTIONS.md").write_text(
        _BUILD_INSTRUCTIONS.format(stem=stem), encoding="utf-8"
    )

    # 4. schematic.json for traceability
    (output_dir / "schematic.json").write_text(
        json.dumps(schematic, indent=2), encoding="utf-8"
    )

    return {
        "ok": True,
        "output_dir": str(output_dir),
        "files": [p.name for p in sorted(output_dir.iterdir())],
        "units": len(schematic.get("units", [])),
        "streams": len(schematic.get("streams", [])),
        "sumoslang_lint": lint,
        "next_step": f"Open {output_dir / 'BUILD_INSTRUCTIONS.md'} and follow the 5-step procedure.",
    }


# ---------- Apply schematic to a verified baseline (Tier 1) ---------------

def apply_to_baseline(schematic: Dict[str, Any],
                      baseline_sumo: str | Path,
                      baseline_dll: str | Path,
                      output_sumo: str | Path,
                      *,
                      strict: bool = True) -> Dict[str, Any]:
    """
    Tier 1 path: copy a known-good (.sumo + .dll) pair, then apply every
    parameter override from the schematic via SumoCore.

    This does NOT change topology. It only changes parameters that exist
    in the baseline. If `strict=True` (default), the function refuses to
    proceed when any schematic parameter does not resolve to a baseline
    variable.
    """
    baseline_sumo = Path(baseline_sumo)
    baseline_dll = Path(baseline_dll)
    output_sumo = Path(output_sumo)
    output_dll = output_sumo.with_suffix(".dll").with_name("sumoproject.dll")

    if not baseline_sumo.exists():
        raise FileNotFoundError(f"baseline_sumo not found: {baseline_sumo}")
    if not baseline_dll.exists():
        raise FileNotFoundError(f"baseline_dll not found: {baseline_dll}")

    # 1. Copy the verified pair to the output location.
    output_sumo.parent.mkdir(parents=True, exist_ok=True)
    shutil.copy2(baseline_sumo, output_sumo)
    shutil.copy2(baseline_dll, output_sumo.parent / "sumoproject.dll")

    # 2. Collect every parameter override from the schematic.
    overrides: List[tuple[str, float, str]] = []
    for u in schematic.get("units", []):
        for p in u.get("parameters", []):
            sv = p.get("sumo_variable")
            if sv:
                overrides.append((sv, float(p["value"]), u["id"]))

    # 3. Resolve against the baseline's state.xml (sibling to the .sumo).
    state_xml = output_sumo.parent / "state.xml"
    known_vars = _read_state_variable_names(state_xml) if state_xml.exists() else set()

    resolved, unresolved = [], []
    for sv, val, uid in overrides:
        if not known_vars or sv in known_vars:
            resolved.append((sv, val, uid))
        else:
            unresolved.append((sv, uid))

    if strict and unresolved:
        return {
            "ok": False,
            "reason": "schematic references variables not in baseline",
            "unresolved": unresolved[:20],
            "unresolved_count": len(unresolved),
            "hint": "Either change the baseline, edit the schematic to match it, "
                    "or call apply_to_baseline(..., strict=False) to apply only the "
                    "subset that resolves.",
        }

    # 4. Write the overrides into state.xml using the existing persistence
    #    helper if available. We import it lazily to avoid a circular dep.
    try:
        from server import _persist_parameters_into_state_xml  # type: ignore
        _persist_parameters_into_state_xml(state_xml, resolved)
    except Exception as e:
        # Fall back to a .scs script the user can apply manually.
        scs_path = output_sumo.parent / "apply_overrides.scs"
        scs_path.write_text(
            "\n".join(f"set {sv} {val};" for sv, val, _ in resolved) + "\n",
            encoding="utf-8",
        )
        return {
            "ok": True,
            "mode": "scs_fallback",
            "output_sumo": str(output_sumo),
            "apply_script": str(scs_path),
            "applied": len(resolved),
            "skipped": len(unresolved),
            "note": f"In-process persist failed ({e!s}); applied overrides written to {scs_path.name} for manual application in SUMO Core Window.",
        }

    return {
        "ok": True,
        "mode": "persisted",
        "output_sumo": str(output_sumo),
        "applied": len(resolved),
        "skipped": len(unresolved),
    }


def _read_state_variable_names(state_xml: Path) -> set[str]:
    """Return the set of variable names declared in a SUMO state.xml."""
    import xml.etree.ElementTree as ET
    try:
        tree = ET.parse(state_xml)
    except ET.ParseError:
        return set()
    return {el.get("name") for el in tree.iter() if el.get("name")}
```

## Appendix A — Known facts about SUMO `.sumo` files

- Always paired with a `sumoproject.dll` in the same directory; SUMO refuses to open the `.sumo` without it.
- `state.xml` is produced by the SumoCore command `save "state.xml";`, not constructed externally.
- `sumoproject.dll` is compiled from a SumoSlang plant definition by SUMO's compiler; the symbol table inside the DLL must match the variable names referenced in `state.xml` and in any `set` commands.
- The file is opened by SUMO via its own loader, which expects a specific internal layout (not documented in this project's source materials, so do not assume `zipfile` round-tripping is sufficient).

## Appendix B — How to produce a known-good baseline

From `README.md`, the only documented path:

1. Build the plant in SUMO24 GUI.
2. Click **Simulate** and wait for "Ready for simulation".
3. Open **Advanced → Core Window** and run `maptoic; save "state.xml";`.
4. Copy `state.xml` and `sumoproject.dll` out of the SUMO project directory.
5. Save the `.sumo` file from SUMO's **File → Save** menu.
6. Place all three (`<name>.sumo`, `state.xml`, `sumoproject.dll`) into `F:/UNI/SUMO/MCP/baselines/`.

This is the **only** way to obtain a SUMO-loadable `.sumo` file. The MCP server's job is to drive parameters against it, not to manufacture it.
